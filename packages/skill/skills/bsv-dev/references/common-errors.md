# Common BSV errors and what to do

Applies to: both
Guardrails: G-01, G-09, G-11, G-12, G-13, G-18, G-21, G-29, G-32

Find the message or symptom, read the cause, apply the fix. For a known txid, read its status first (`arcade_status`, or `scripts/arcade-check.sh <txid>`): Arcade's answer is the truth for that transaction. Arcade 400 answers carry a numeric `status` code that keeps the legacy ARC numbering; Arcade does not serve the ARC API itself (`arcade-0conf.md`, "Classify 400s").

| symptom | cause | fix |
| --- | --- | --- |
| `internalizeAction` throws `WERR_INVALID_PARAMETER` … "must be a complete, exactly framed Atomic BEEF" | The AtomicBEEF misses an unconfirmed ancestor or the merkle path of a confirmed one, or is not framed on the transaction being internalized. | Include every unproven ancestor back to mined transactions with their proofs. Build it from BEEFs you already hold plus Arcade's `rawTx` (re-read as plain), then `beef.toBinaryAtomic(txid)` (`payments-brc29.md`). |
| `Invalid isAuthenticated result` at login | In `@bsv/sdk` 3.2.1, `isAuthenticated()` throws on a locked wallet instead of returning `false`. | Call `waitForAuthentication()` and never gate on `isAuthenticated()` (`wallet-brc100.md`). |
| `No wallet available over any communication substrate` | No BRC-100 wallet is running, so `connectToSubstrate()` rejects. | Tell the user to install and open a BRC-100 wallet such as BSV Desktop (local ports 3321 and 2121), then retry. |
| `FEE_TOO_HIGH` from the app's own fee check | The cap or estimate assumed a size far below the serialized transaction, for example a few hundred bytes for a draft carrying a 9.6 KB output. | Size the fee from the serialized draft at the configured rate (default 100 sat/kB), never below what `GET /policy` reports. Cap only where an overpay would harm a counterparty (`testnet-to-mainnet.md`). |
| Arcade 400 with `status` 476 | Not final: `nLockTime` is ahead of median-time-past and an input is non-final. Transient; nothing was persisted. | Re-post the identical transaction after the lock time passes, on a bounded schedule. |
| Arcade 400 with `status` 466 (`UTXO_SPENT`), sometimes about 20 ms after a 2xx | Another transaction spends one of the inputs. Terminal for those bytes, unless the competitor is your own earlier copy. | Read `GET /tx/{txid}` and its `competingTxs`. If the competitor is yours, it is not a failure. Otherwise apply the two-read dead rule before re-planning with other coins (`arcade-0conf.md`). |
| Arcade 400 with `status` 465 | Fee too low for the instance's `/policy`, for example testnet's 1 sat/kB sent to mainnet. | Re-size the fee from the serialized transaction at the configured rate (default 100 sat/kB), never below what `GET /policy` reports, and sign again. |
| Arcade 400 with `status` 461 | A malformed transaction or an invalid unlocking script. | Fix the transaction. Validate every input with `@bsv/sdk` `Spend` before broadcasting. |
| Arcade 400 with `status` 460 | Not Extended Format: Arcade needs each parent's output data. | Attach `sourceTransaction` to every input and send `tx.toHexEF()`; never send BEEF. |
| A 2xx from `POST /tx`, then `REJECTED` | The POST answer is provisional; Arcade can reject about 20 ms later. | Always read `GET /tx/{txid}` after a submit and gate on that. |
| Arcade `GET /tx/{txid}` 404 after a wallet broadcast | The user's wallet broadcast through its own services, so this Arcade never saw the txid. A 404 is no verdict, not a rejection. | Submit it yourself: convert the `createAction` AtomicBEEF with `Transaction.fromAtomicBEEF(tx).toHexEF()`, `POST /tx` (idempotent), then read the status. |
| WhatsOnChain HTTP 429 | More than about 3 requests per second from one IP, often ungated calls from several places. | Route every call through one process-wide gate (at least 350 ms apart) with backoff on 429. Ask Arcade, not WhatsOnChain, about any txid you know. |
| WhatsOnChain 404 on a fresh transaction (`/tx/{txid}/hex`) | Not indexed yet: WhatsOnChain indexes an unconfirmed spend 6–12 s late. | Treat it as "not yet", never as "does not exist". Read the transaction from Arcade instead. |
| `UTXO_SPENT` on a coin WhatsOnChain's `/address/{a}/unspent` still lists | WhatsOnChain keeps listing coins spent by an unconfirmed transaction until that transaction is mined. | Check `/tx/{txid}/{vout}/spent` before spending, mark a coin spent the moment you select it, and never trust a listing alone. |
| Every browser page importing `runar-sdk` crashes in `fileURLToPath(import.meta.url)` | Rúnar's `runar-ir-schema` calls `fileURLToPath(import.meta.url)` at load, a Node-only call. | Alias `node:url`, `node:path` and `node:fs` to browser shims in the bundler, and add a build check that fails on any unshimmed Node builtin. |
| `Undelayed createAction or signAction results require review` (`WERR_REVIEW_ACTIONS`) | With `acceptDelayedBroadcast: false`, the wallet's own broadcast did not succeed. Per `@bsv/sdk` 3.2.1, `reviewActionResults` gives each txid's status: `serviceError` (queued for delayed retries), `doubleSpend` (with `competingTxs`) or `invalidTx`. The error may carry only the txid, without `tx`, and an empty txid means a double spend found before the transaction was built. This handling is not yet tested against BSV Desktop; one testnet observation saw it when a second undelayed action followed the first within about 3 minutes. | Read `reviewActionResults`. On `serviceError`: when `tx` (AtomicBEEF) is present, submit `Transaction.fromAtomicBEEF(tx).toHexEF()` to your own Arcade and gate there; when it is absent, read `GET /tx/{txid}` for the txid given; with an empty txid, treat the action as not broadcast. On `doubleSpend`, apply the two-read dead rule and do not pay again. On `invalidTx`, fix the transaction. Space chained undelayed actions. |
| `arcade_submit` answers `mainnet broadcast disabled; set BSV_MCP_ALLOW_MAINNET_BROADCAST=1` | The `bsv-mcp` server refuses agent broadcasts on mainnet unless the user has set that flag. Expected. | Agents: never set the flag yourself. Tell the user what you want to broadcast; only they decide to set it, and you still ask before each mainnet broadcast. Apps do not use this flag (`testnet-to-mainnet.md`). |
| `BSV_NETWORK must be testnet or mainnet (got: …)` at boot | `scripts/network-guard.sh` read a value such as `main` or `test`. | Set `BSV_NETWORK` to exactly `testnet` or `mainnet`. |

Docs: resolve `guides.services.broadcasting` with `docs_url`, or `search_docs` the message text on the BSV docs MCP.
